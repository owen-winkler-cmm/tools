# /cmemail

Produce a Change Submission email from a Jira ticket **only when it will earn a plain "approved" from SLM**. This skill is a readiness gate first and a drafter second. It gathers what the ticket, PR, and the conversation prove (description, components, linked STCM/team-card, linked PR, assignee, approvals, back-out plan, testing evidence, window), then checks that every field an SLM reviewer scans for is both present and backed by a fact. If it all is, it writes the email. If anything is missing, it doesn't just bounce: it shows the full list of gaps and then **interviews the user through them one at a time**, each with an example of a good answer, merging each reply in before moving on. Sourced facts are plain prose with an inline citation; the skill never invents a fact to clear the gate. The sole exception that can't be collected this way is a required approval -- that must actually be on the PR, so the interview can prepare everything else but the email still waits on the real approval.

Why a gate and not a draft-with-blanks: a produced email gets sent as-is, often by someone who won't edit it and doesn't know `finalize` exists. A blank that a reviewer bounces, or an approval line that was accurate at draft time but stale by send time, both do real harm. The reliable fix is to never hand someone a sendable artifact that isn't actually ready -- and, rather than leave them to figure out why it bounced, to walk them through making it ready.

The readers are SLM, executive/VP leadership, and risk reviewers deciding whether to approve a change -- not the engineers who'll run it. Every field that describes what could go wrong leads with the business, customer, or downstream consequence; the technical mechanism is the "because" that backs the claim up, not the claim itself. See "Business framing" under Composition rules.

**Template:** `.claude/assets/cmemail/change-submission-email-template.md` -- the field-by-field contract and the filled example. Read it before composing; do not paraphrase the section names or reorder them.

## Inputs

- `<TICKET-KEY>` -- a Jira issue key (any project prefix, e.g. `STCM-4821` or `PARCH-2290`). Case-insensitive; uppercase before use.
- A PR/diff URL (`github.com/...` or `git.innova-partners.com/.../pull/\d+`) -- in practice this is the more common invocation, not a fallback. Resolve the ticket key from the PR (step 1) and proceed exactly as if that key had been typed directly; the PR itself is also the Change-set link, so it doesn't need re-deriving later. Only report a failure here if the PR genuinely has no discoverable linked Jira ticket -- receiving a PR URL instead of a bare key is the normal case, not something to complain about.
- **Supplemental facts in the prompt** -- any free text after the key/URL supplies facts the ticket or PR doesn't carry (e.g. "back-out: scale the schedule config back to the prior value via `argocd app set`, ~5 min; tested in integration 2026-10-06"). These are used as a source and merged into the draft **silently** -- treated exactly like a ticket-sourced fact, with no provenance note and no "(from ...)" citation. This is the normal way to clear a gate block without editing the ticket. The no-fabrication rule is unchanged: the skill still invents nothing; it only uses facts the ticket, the PR, or the user actually provided.

## Modes

- **Generate** (a ticket key is given): build the draft (steps below).
- **`finalize <file>`**: strip the working glyphs (✍️ 🚧) and their backticks from a finished draft in place, leaving clean prose ready to paste into an email client. Make no other edits.

## Preflight (Generate mode only)

Before doing anything else -- before fetching the ticket, before anything -- confirm every connection this skill depends on is actually up. Run all three checks below regardless of whether an earlier one already failed -- don't stop at the first failure, so the report can name every broken connection at once instead of making the user fix one, re-run, and discover the next. Only after all three have been attempted: if any failed, stop right there and report all of them together, with what to do about each; do not fetch the ticket, do not write a draft, do not produce partial output. A degraded or partially-sourced draft is worse than no draft, since the whole point of this skill is to be decisive about what it knows, not to guess around gaps caused by a dead connection.

1. **Atlassian Rovo MCP** -- required for every run. Confirm it's live with a cheap call (e.g. `atlassianUserInfo`). A tool-not-found error or an auth failure means it's down.
2. **`gh` CLI** -- required for every run (approvals, step 5, depend on it). Run `gh auth status` and confirm at least `github.com` and `git.innova-partners.com` show as logged in and active -- those are the two hosts this org's repos live on.
3. **Datadog MCP** -- required for every run (Systems affected, Dashboards, Muted alerts, and PagerDuty routing all depend on it). Confirm `plugin:datadog:mcp` tools are actually callable with a minimal call (e.g. `search_datadog_dashboards` with a trivial query). If the tools aren't in the tool list at all, that's the failure -- direct the user to the `datadog:ddsetup` skill rather than trying to work around it.

Only proceed to step 1 once all three check out.

## Generate -- steps

1. **Fetch the ticket.**
   - If given a PR/diff URL instead of a bare ticket key, resolve the key first: fetch the PR's description (`gh pr view <number> --repo <owner>/<repo> --json body`, prefixing `GH_HOST=<host>` for a non-github.com host) and extract the Jira reference (`[A-Z]+-[0-9]+` or a Jira browse URL). This is the common case, not an exception -- only stop and report a failure if the PR's description has no discoverable Jira reference at all. The PR URL itself is already the Change-set link (step 3) once resolved this way; no need to re-derive it later.
   - `getJiraIssue`, `cloudId: covermymeds.atlassian.net`, fields: `summary, description, status, priority, labels, components, assignee, reporter, issuelinks, comment, duedate, fixVersions, project`. Also fetch remote issue links (`getJiraIssueRemoteIssueLinks`) for PR/build links Jira's dev panel tracks outside `issuelinks`.

2. **Resolve the STCM / team-card pair.**
   - If `<TICKET-KEY>` matches `STCM-\d+`, it IS the STCM record. Scan `issuelinks` for a linked non-STCM issue (any relationship) to use as the team card.
   - Otherwise `<TICKET-KEY>` is the team card. Scan `issuelinks` for a linked `STCM-\d+` issue.
   - If no counterpart is found either way, proceed with only the one ticket you have. Not every change requires an STCM -- when none applies, the Jira team card itself is the change record, not a placeholder awaiting one. Never write "STCM pending" (or any equivalent) anywhere in the output.

3. **Extract auto-fillable facts.** Only pull a field if it is literally present or a direct, mechanical derivation of something literally present (e.g. the template's own tier-to-duration rule once tier is known); do not infer or paraphrase compliance claims. Candidates, by template field:
   - **Change / subject description** -- ticket summary, cleaned of any leading key/tier annotation the ticket itself appends (e.g. strip a trailing `(RMT: Medium)`).
   - **Systems affected** -- this asks which *other* systems, services, or clients are exposed to this change's blast radius, not which files or workflows changed inside this repo. Name the business-facing surface where one is knowable (a customer portal, a payer-facing workflow, a named client) and use the technical service name as the supporting detail behind it, not the headline -- e.g. "the customer PA portal, which depends on diagnosis-api for drug lookups" rather than bare "diagnosis-api." When no business-facing mapping is knowable from the ticket or the dependency data, name the technical service plainly; don't invent a customer-facing label the sources don't support. Has its own source path -- see step 4.
   - **Production reach** -- the business/customer effect if this affects production, stated first, technical mechanism as the reason: "Would prevent CVS users from logging in, because it changes how the OIDC callback validates tokens." No production impact at all: say so plainly (a valid, sourced answer). Affects production but the ticket doesn't support a specific business effect: don't invent one -- the missing effect is a gate block (step 6), with the technical mechanism noted as context for the user to resolve. Reason from the ticket's own risk review, description, and Done-When; write as plain sourced prose, not a bare Direct/Indirect label.
   - **Requested tier** -- only if the summary, description, or labels literally contain a risk-tier line matching `RMT:\s*(Low|Medium|High|Critical)` or `Tier:\s*(...)` (whichever literal field name the ticket itself uses). When citing this in the output, describe it in plain language (e.g. "the risk review on the ticket's Jira card") -- never write the ticket's internal field-name acronym into the composed email. Never derive tier from Jira `priority` -- that field measures urgency, not change-management risk tier, and conflating them is exactly the kind of unsupported claim this skill must not make. The tier's "because" impact justification must itself be sourced: if the cited risk-review text argues from business/customer consequence, use it; if it argues from effort/scope of work, or no justification exists at all, that is a gate block (step 6, "Tier justified by effort, not impact"), not a shippable line.
   - **Risk-and-readiness narrative** -- where the ticket's risk review, description, Done-When, or HOW text speaks directly to a numbered item (business impact, testing already done, a plausible rollback mechanism given the nature of the change), write it as plain sourced prose citing the ticket. Where the ticket doesn't cover something a numbered item requires (tested evidence, recovery time, blast-radius confirmation), that gap is a gate block (step 6), not a hedge shipped inside the answer. Never launder ticket prose into an unqualified compliance claim. Item 1 especially: if the ticket only states the technical failure mode ("the cache layer would be unavailable") without naming who or what downstream feels it, connect the two using only what the ticket or Systems affected data actually supports -- lead with the downstream/customer consequence and cite the technical fact as the reason, rather than reproducing the technical statement as if it answered the business-impact question on its own.
   - **Risk-and-readiness item 4** ("who has to be available") -- defaults to the same deployer/implementer used elsewhere (see Checks to run below), same reasoning: the deployer runs the in-window validation, and the implementer is the deployer unless the ticket says otherwise.
   - **Risk-and-readiness item 5** ("how will they be reached") -- the reachability answer belongs in Named Resources; point to it rather than resolving (or blocking on) reachability twice.
   - **Post-deployment verification plan** -- an explicit Done-When end-to-end test or acceptance check maps directly to Checks to run / Pass criteria; use it plainly, sourced.
   - **Monitoring duration** -- once tier is known, the template's own rule (24h for Low/Medium, 48h for High/Critical) is a mechanical derivation, not an inference -- fill it in and cite the rule.
   - **Named resources: Implementer** -- the assignee, offered as a candidate value, not asserted as fact (assignee and implementer are usually but not always the same person).
   - **Named resources: Validator** -- well known from the approvers list (step 5), not a separate human-fill blank in the normal case. GitHub/GHE won't let the implementer approve their own PR, so every name in the approvers list is already distinct from the Implementer. Pick whichever approver isn't the one serving as manager/director sign-off (the human's own statement about which approval counts as their manager/director sign-off takes precedence -- e.g. an approval from the person who is both manager and director covers that slot, freeing up any other approver as Validator). If only one name is on the approvers list total, don't fabricate a second -- that leaves no distinct Validator, which is a gate block (step 6, "Named resources as specific individuals"), not a blank to ship.
   - **Post-deployment verification plan: Checks to run** -- the deployer runs these checks, and unless the ticket specifies a different deployer, the deployer is the Implementer. Name them directly instead of leaving "who runs each check" blank.
   - **Post-deployment verification plan: Rollback trigger** -- once Pass criteria is established, derive this as its plain-language negation ("not seeing the success criteria") rather than requiring the human to invent a separate threshold: if Pass criteria is "X returns green and Y succeeds," Rollback trigger is "X does not return green, or Y fails." If the only trigger derivable reads as a vague judgment call ("if it looks bad") rather than a concrete observation, that's a gate block (step 6), not a shippable line.
   - **Post-deployment verification plan: Rollback decision** -- check the Jira card and the GitHub/GHE PR (description and comments) for an explicit statement naming a different rollback decision-maker before defaulting. If none is found, defaults to the same deployer/implementer named in Checks to run, deciding based on their own observation of whether the Rollback trigger fired -- state this plainly, without mentioning that a check was made (see "Don't narrate process" below). If the ticket or PR does name someone else, use that person instead and cite where it came from.
   - **Links** -- STCM record and team card URLs (from step 2). Change set link: if the run started from a PR URL (step 1), that's already the Change-set link -- just use it, no re-deriving and no citation. Otherwise scan the description, comments, and remote issue links for a PR/diff URL (`github.com/...` or `git.innova-partners.com/.../pull/\d+`).
   - Anything an SLM reviewer scans for that has no source and no mechanical derivation (the specific rollback decision-maker, validator identity, proposed window date/time, dashboard links, exact reachability channels) is a gate block in step 6, not a shippable blank -- the only blanks a produced email may carry are the To/Cc delivery lines. Approvals have their own source path -- see step 5.

4. **Look up Product/Operations counterparts, Systems affected, and Datadog monitoring.** Determine the affected service name(s) from the repo name in the Change-set link (or an explicit system name in the ticket).
   - **Systems affected** -- prefer a fresh call to `mcp__plugin_datadog_mcp__search_datadog_service_dependencies` with `direction: upstream` for the service (upstream = services that call into it, i.e. who's exposed if it breaks). List the caller services, cited "(from Datadog service dependencies)" -- but state what each one actually is to the business (a named customer portal, a payer-facing workflow) wherever that's already knowable from the ticket or the service-directory cache, rather than relaying a bare technical service name as if it told SLM something on its own. Fall back to the service-directory cache's `dependencies.upstream` snapshot (citing its `capturedAt` date) only if that MCP isn't connected. If neither source has the service, Systems affected has no answer and the run is a gate block (step 6) -- never substitute the internal files/workflows changed in the repo for this field.
   - Use the cache's `operationsCounterpart` / `productCounterpart` as plain sourced text -- state it directly, with no "(from service directory)" citation appended (see "Don't narrate process"). Confidence still matters, just not as a citation: a `confirmed` entry is written as flat fact; an `inferred` or `unconfirmed` entry keeps its caveat inline (e.g. "covering by default, not yet confirmed for this service") since that's a live uncertainty for the reader, not sourcing narration. Don't launder a lower-confidence entry into a flat assertion.
   - A `name: null` / `confidence: "unresolved"` entry means don't fabricate a name -- it's a gate block (step 6), with the specific gap named in the reason (e.g. `No product counterpart identified for requests-api.`) so the user isn't rediscovering it from scratch. It clears when the name is added to the cache, the ticket, or the prompt.
   - Normalize any team reference to **Shared Capabilities** -- the cache's other names for it (Dumpster Firefighters, Plat-Mod) and Confluence's stale ones (Plat-MAC, Platform MAC) are aliases/errors, not distinct teams; see the cache's `team` and `staleAliases` blocks.
   - If the cache file doesn't exist, or the service isn't in it, the counterparts must come from the ticket or the prompt; absent those, it's a gate block (step 6). The cache is a convenience for known services, not a requirement.
   - **Dashboards** -- search `mcp__plugin_datadog_mcp__search_datadog_dashboards` for the service by name. A plain name search can surface false positives (e.g. an unrelated dashboard whose title happens to contain the search term) -- prefer a dashboard whose title matches the service, and also check whether the service's own monitors (below) reference a shared/templated dashboard (e.g. an "Application Heartbeat Dashboard" parameterized by app name) -- that's a legitimate link too even if it's not a dedicated per-service dashboard. Cite "(from Datadog)". If nothing turns up, the Dashboards field has no answer and the run is a gate block (step 6).
   - **Muted alerts** -- search `mcp__plugin_datadog_mcp__search_datadog_monitors` with `query: "service:<name> muted:true"`. If none are found (the common case), write it plainly -- "No monitors currently muted for <service> (checked via Datadog)" -- rather than leaving a blank. List any that are found, by name.
   - **Who is watching** -- once the operations counterpart is resolved (above), state monitoring is handled via that team's PagerDuty on-call rotation rather than leaving a human-fill blank; PagerDuty coverage is inherently 24/7, which already satisfies the "not just the implementer's workday" concern (see 🚧 mapping). Name the actual PagerDuty routing key if a `service:<name>` monitor search (above) surfaces one in a monitor's `notifications` (e.g. `@pagerduty-platform-dumpster-firefighters`) -- no trailing "(from ...)" citation needed.

5. **Fetch approvals and resolve roles.** These live on the GitHub/GHE PR or the STCM record, not on the team card. Pull them, then match each approver against the role registry (`.claude/cmemail/approvers.json`) so the gate (step 6) can check that the tier's required roles are actually approved. The approvers *list* shown in the email still carries no inferred role label -- role resolution is for the gate, not for annotating names in the body.
   - **No-STCM flow:** fetch the Change-set PR's reviews and keep any with `state == APPROVED`: `gh api repos/<owner>/<repo>/pulls/<number>/reviews` (prefix `GH_HOST=<host>` for a non-github.com host, e.g. `git.innova-partners.com`). Take the most recent review per distinct reviewer (a later `CHANGES_REQUESTED` or `DISMISSED` cancels an earlier `APPROVED` -- only a *current* APPROVED counts). Match each approver's `user.login` against `approvers.json` `roles` for the run's host: a login in `roles.em` satisfies **em**, `roles.director` satisfies **director**, any other APPROVED reviewer who is not the PR author satisfies **peer**. List everyone found under **Approvers:** with name + approval date -- no "(from ...)" citation and no role label (see "Don't narrate process").
   - **STCM flow:** check the STCM ticket's own status and fields for approval signals (e.g. a workflow status like "Manager Review Still Needed" vs. an approved state, or any approval-related custom field returned by `getJiraIssue`) and resolve roles the same way where the record names the approver.
   - **Never present a self-referential CI gate as approval state.** A check like `itgc-checks` that stays red until the EM approves is red *by construction* at draft time; it encodes "EM hasn't approved yet" and keeps saying so even after they have. Do not report its status as an approval signal anywhere -- read the approval from the review itself, not from the gate that the approval turns green. (Same trap `/emreview` already guards against.)
   - **The gate verifies only approvals that land in the source.** The EM role (currently Owen Winkler) also holds Director, so a single APPROVED review from the EM is the combined EM/Director sign-off -- Director is never gated separately. **VP approval is obtained through the generated email, not the PR or Jira** (the VP is a recipient who approves by reply), so its absence from the source is expected and must never be a block: do not add a VP role to the gate. See `approvers.json` `vpApproval`.
   - This is the one place this skill reads GitHub/GHE PR data beyond the link itself -- reviews only, never the PR body or general comments (those stay out of scope; see Notes).

6. **Readiness gate -- resolve every gap before composing, interactively.** Run this after everything is gathered (steps 1-5) and before composing a single line. Evaluate every condition below against the ticket, the PR, and anything supplied so far in the conversation. For each gap, classify it:
   - **Collectable** -- a fact the user can provide in conversation: back-out steps, back-out timing, testing/validation evidence, deployment window, product/operations counterpart, dashboards, rollback decision-maker, an impact-based tier justification, or any other SLM-answer field lacking a fact.
   - **Source-only** -- state that must exist in the record and cannot be supplied by an answer without fabricating it: a required approval (`peer` or `em`) not present on the PR/STCM record. Typing "yes, it's approved" does **not** satisfy this; the approval has to actually be on the PR, so this is never an interview question. (VP approval is never gated -- see step 5.)

   **No gaps:** go straight to compose (step 7).

   **Gaps present -- do not terminate; run an evidence interview:**
   1. **Show the whole list first**, collectable items and source-only blockers together, each named plainly (use the Gap wording below), so the user sees the full scope before answering anything.
   2. **Collect the collectable gaps one at a time, over as many turns as it takes.** For each: ask the single question, and show a one-line example of what a good answer looks like (draw it from the template's filled example and the 🚧 rubric) so the user knows the bar. Take the user's answer and merge it silently as a source (per Inputs). If the answer is still contentless -- "yes," "we'll back it out," a team name where SLM wants a person -- say so, show the example again, and re-ask; do not accept it and do not invent a stronger version on the user's behalf. Ask one at a time, but if the user answers several at once, take them all. Never mark an item done until it has a substantive fact behind it.
   3. **Offer to capture the collected facts for the record.** Once collected, offer a short summary the user can paste onto the ticket/PR so the evidence is durable and the audit trail exists. Optional -- the draft doesn't depend on it.
   4. **Source-only blockers can't be interviewed away.** Keep collecting everything else so the submission is otherwise ready, but state plainly that no email is produced until the real approval lands on the PR. Re-check it against the review when the user says it's done (or on a re-run) -- never take their word in place of the review.

   **Compose (step 7) only when every collectable gap has a substantive answer and no source-only blocker remains.** If the only thing left is a missing approval, produce no email yet; tell the user the content is ready and the one remaining step is the approval on the PR.

   **Gap wording** (for the opening list and any re-ask):
   - `No current peer approval on the PR.` / `No EM approval on the PR (expected: <name from roles.em>).` / `EM approver login not configured in approvers.json -- cannot verify EM approval.` *(source-only; resolve on the PR, not in chat)*
   - `No back-out steps found.` (the concrete actions, not "we will back it out")
   - `No back-out recovery timing found.` (a duration)
   - `No testing/validation evidence found.`
   - `No deployment window (start and end timestamp) found.`
   - `Requested tier is justified by effort/scope, not business impact.` (heuristic from the rationale text; skip when it clearly argues from consequence)
   - `<Field> has no substantive answer (would answer "<the contentless value>").` for any other SLM-scanned field: tier justification, Systems affected, Production reach, the five Risk-and-readiness items, Named resources as specific individuals, Checks to run / Pass criteria / Rollback trigger / Rollback decision, Who is watching.

   The only blanks a produced email may still carry are the To/Cc delivery lines (see Address-to-confirm and Cc rules); those are never interview items and never block.

7. **Compose** the subject line and body per the composition rules below, using the template's structure verbatim. (Reached only when step 6 is fully satisfied.)

8. **Write** to `cmemail-<ticket-key-lowercased>.md` in the working directory (e.g. `cmemail-stcm-4821.md`). Show a brief preview in conversation; the file is the deliverable.

## Composition rules

**Formatting.**
- Field labels are **bold** (e.g. **Change:**, **Requested tier:**, **Rollback trigger:**) -- one space after the label, nothing more.
- Never use square brackets for a blank. The only blanks a produced email carries are the To/Cc delivery lines, written as a backtick-wrapped span with the glyph inside the backticks, e.g. `` `✍️ SLM distribution -- confirm address with SLM before first submission` ``. Every content field is filled with a fact or it blocked the run at step 6; it never ships as a blank.
- No extra spacing, tabs, or manual column alignment anywhere in the body. Don't pad labels to line up colons across lines -- let lines wrap naturally.
- Plain sourced facts get no glyph and no backticks -- just prose with an inline citation, e.g. "(from PARCH-1050)" or "(from service directory, confirmed by Owen Winkler, 2026-08-11)".
- The email body itself is bare markdown, not fenced in a code block.
- **Business framing.** This email's readers are SLM, executive/VP leadership, and risk reviewers deciding whether to approve a change -- not the engineers who'll run it. Any field describing what could go wrong (Systems affected, Production reach, Risk-and-readiness item 1, and anywhere else an impact gets stated) leads with the business, customer, or downstream consequence; the technical mechanism is the "because" that backs the claim up, never the headline it replaces. "This could make the customer PA portal unable to process drug information" is the right register; "diagnosis-api's redis instance would be offline" is the reasoning behind that statement, not a substitute for it. Still cite the concrete technical fact -- don't go vaguer than the ticket supports, just don't lead with it. Don't invent the effect if the ticket doesn't support one -- that's a gate block (step 6), not a guess.
- **Direct-answer-first (ELI5).** SLM reviews against their own fixed intake checklist, not by reading paragraphs top to bottom -- they scan for a direct, standalone answer to specific literal questions ("the deployment start date and time," "the deployment end date and time," "are product and operations counterparts aware and available in real time," "estimated time to complete rollback," "the name of the individual performing post-deployment validation") and send the email back for anything they can't find stated plainly, even when a longer paragraph elsewhere already covers it. State the literal answer to each of those in one short, plain sentence before any supporting nuance -- write it the way you'd explain it to someone with no context, not the way you'd explain it to another engineer.
  - **Match the question's grammatical form.** The first sentence answers in the form the question actually asks. A "how would it hurt...?" question is open-ended: lead with the named harm, or "NO HARM, because...", never a bare "Yes" (answering an open question with "yes" is exactly the kind of non-answer SLM bounces). A yes/no question leads with "YES" or "NO." A "what is...?" question leads with the thing itself. Do not reflexively open every item with yes/no.
  - **CAPITALIZE the scannable answer.** In that first sentence, put the exact phrase SLM is scanning for in ALL CAPS so it can't be missed (e.g. "DELAYED PRIOR-AUTHORIZATION EVENTS ...", "We are CONFIDENT OUR TESTING HAS MITIGATED THE RISK ..."). Caps, not bold: the body gets pasted into an email client as plain text, where markdown bold disappears but caps survive. Capitalize only the definitive answer span, not whole sentences.
  - **The first sentence must carry a fact, never a bare affirmation.** "Yes," "it was tested," "we will back it out," "capacity will be restored" are non-answers; the sentence has to name the actual steps, environments, numbers, or named people that make the answer true. (This is the same bar the gate enforces in step 6 -- if no such fact exists, it never reaches composition.)
  - **Proposed window** is always two explicit single-point timestamps -- one start, one end -- never a range, a multi-day span, "any time works," or a description of flexibility in place of the two values. Its length covers deployment and in-window validation only; post-deployment monitoring time (the 24-48h tier rule) never gets folded in, even for a change with a long soak requirement -- that belongs only in Monitoring after business hours resume.
  - **Risk-and-readiness item 1** ("...how would it hurt our business, revenue, or client relationships?") is a "how" question, so it opens with either the named harm in caps ("DELAYED PRIOR-AUTHORIZATION EVENTS to downstream services ...") or "NO HARM, because ...", not a bare "Yes" -- answer the question as asked, before any blast-radius or worst-case nuance. A reviewer scanning for the plain answer shouldn't have to read a paragraph of shared-resource caveats to find out whether the honest bottom line is "no harm."
  - **Risk-and-readiness item 2** states the back-out steps and the recovery time as their own short clauses ("back-out: revert the schedule config via X; recovery time: under 10 minutes") even when the surrounding sentence already implies them.
  - **Risk-and-readiness item 3** answers SLM's real question, which they phrase as confidence ("are you confident in this change based on testing and validation?"). Lead with a capitalized confidence verdict tied to fact, not a recitation of what ran: "We are CONFIDENT OUR TESTING HAS MITIGATED THE RISK OF THIS CHANGE, from <specific tests> in <specific environments> and passing <the automated checks designed to catch this class of change>." Then the supporting evidence. A bare "it was tested" or "all checks passed" with no confidence verdict is what leaves SLM re-asking whether you're actually confident.
  - **Risk-and-readiness items 4-5** state counterpart real-time availability as an explicit "Yes -- <names> are aware and available" (or "No -- ..."), not just a sentence that happens to name them in passing.
  - **Named resources: Validator**, and whoever is named in **Checks to run**, is always a specific person -- never a team name, even when a team is legitimately the on-call owner. Name the individual currently holding that rotation, or the person coordinating it.
- **Answer, evidence, mitigation -- in that order.** Required disclosures don't get trimmed: Systems affected's direct callers and Risk-and-readiness item 1's blast radius stay in every draft, exactly as far as the ticket's own risk review and Datadog's dependency data establish them -- that's not the failure mode. What draws a follow-up is adding a claim beyond what's required, because every extra claim is itself something a reviewer can separately question, and the goal is passing review on the first email, not maximum thoroughness. Compare the two real outcomes. STCM-18886 was approved with no clarification round at all; its item 1 answer is three clauses, in order -- the direct answer, the mechanism that makes it true, the consequence that follows -- and stops: "None -- if something is wrong, the change simply fails safely before anything is created, changed, or deleted, so no downstream system or client is ever exposed (from PARCH-1085)." STCM-18902 drew a clarification asking "are we confident in the change based on testing, validation, and automation?" -- even though testing evidence existed (PARCH-1073, WAF checks against testing/integration) -- because item 1 spent its first two sentences on a second-order chain nobody asked for ("...including requests-api, which is itself called by dozens of downstream systems such as portal, dashboard, patient-portal, mychart, hubservices, hubble, renewals-api, and claims") before ever reaching that evidence. Systems affected only requires the direct callers; tracing who calls those callers is optional elaboration the ticket's own risk review never asked for, and it read as a new, unaddressed risk instead of the diligence it was meant to convey.
  Structure Risk-and-readiness item 1 (and any item shaped like it) in this order, then stop: **the direct answer** first ("No," "None," or the specific hurt named plainly, per Direct-answer-first above); **what was tested or already proven** second, the concrete evidence that makes the answer trustworthy; **the risk that evidence mitigates** third, closing the loop back to the direct answer. Extend past the ticket's required disclosures only when the ticket's own risk review treats the extension as material to the decision -- never just because the dependency data makes it discoverable.
- **Don't narrate process.** This email is for SLM, not an audit log of how this skill worked. State the sourced fact or the applied default decisively; don't explain that a check was made and came back empty ("no override was found, so the default applies"), how a value was mechanically derived ("derived as the negation of Pass criteria"), or hedge with self-referential conditionals ("unless otherwise specified"). A light "(from PARCH-1050)" style citation is fine -- it sources a fact, it doesn't narrate a decision process. Selection reasoning between candidates (e.g. why this approver was picked as Validator over another) also stays out -- name the person, cite the source, move on.
- **Don't ask the human to re-verify what's already been reported.** When content genuinely doesn't exist yet (a date, a name, a decision only a human can make), that's a gate block -- not a "confirm this is still current" / "confirm this covers X" tag bolted onto a fact that's already sourced from the ticket, PR, or a review comment. If a testing result or risk statement is already reported in a primary source, state it plainly and stop; re-verification busywork on top of validation someone already did and documented is exactly what this skill exists to eliminate, not add back in.
- Static boilerplate is **bold**, same as field labels: the section headers (APPROVALS SO FAR, RISK AND READINESS, NAMED RESOURCES, POST-DEPLOYMENT VERIFICATION PLAN, MONITORING AFTER BUSINESS HOURS RESUME, LINKS) and the five numbered Risk-and-Readiness questions themselves. Rule of thumb: if the exact wording would appear in every draft this skill produces, bold it; if it's specific to this change, leave it plain.

**Glyphs.** The gate (step 6) retires `✍️` and `🚧` from SLM-answer fields entirely: a field that used to ship as a `🚧` rejection-risk warning or an `✍️` fact-blank is now a gate block instead -- the email is only produced when that field holds a real fact, so there is nothing left to warn about or ask for inside a produced email. (The `🚧 mapping` below is retained as the catalogue of *why* each field blocks and what a satisfying answer looks like -- it's the gate's rubric, not a set of markers that appear in output.) 🆕 remains retired; a sourced fact is plain prose with a citation.

The one glyph that still appears in a produced email:
- `✍️ ...` -- used **only** for the delivery lines that don't affect SLM's content decision: the **To:** and **Cc:** addresses (see Address-to-confirm and Cc rules). The backtick-wrapped span is the guidance text, glyph inside. Nothing SLM scans for a content answer ever ships as an `✍️` blank.

Add the legend banner right after any front-matter-equivalent line, before the subject:
```
<!-- DRAFT by /cmemail. Every field answering an SLM question is filled with a sourced fact; plain text with a "(from ...)" citation is sourced, not written by you. The only backticked ✍️ spans are the To/Cc addresses -- fill and strip the backticks before sending. -->
```

**🚧 mapping -- the gate's rejection rubric** (from the template's "What gets sent back for more detail" section). These no longer appear as markers in output; they are the catalogue of what makes each field a step-6 block and what a satisfying answer looks like. For each one: if the ticket/PR/prompt supplies an answer that clears the trap, fill the field with that fact; if it doesn't, the field is a gate block (step 6), not a shipped warning:
- **Requested tier:** -- only when the cited risk-review text doesn't already argue from impact/consequence (see step 3). Phrase generically: "a tier justified by effort or scope of work rather than business impact is not sufficient justification" -- never hardcode "not a reason for Low tier" when a different tier is actually being requested; the trap cuts both ways (an under-justified high tier is just as much a problem as an under-justified low one).
- Risk-and-readiness item 2 (rollback / back-out) -- the two things SLM asks for in every bounce are the **actual back-out steps** (the concrete actions, "scale the schedule config back to the prior value via X," not "we will back it out") and a **recovery time** (a duration). Both are hard gate conditions in step 6: absent either, the email is blocked (`No back-out steps found on PR/ticket.` / `No back-out recovery timing found on PR/ticket.`). A satisfying answer names the steps, the recovery duration, and tested evidence for them where it exists.
- **Rollback trigger:** -- "write an observation (a threshold), not a judgment call like 'if it looks bad'"
- **Who is watching:** -- "name overnight and weekend coverage, not just the implementer's workday" -- satisfied automatically when auto-filled via the operations counterpart's PagerDuty rotation (step 4); a gate block (step 6) if no on-call/PagerDuty info turns up anywhere.
- **Implementer:** / **Validator:** -- "if these are the same person, add the explanation SLM will ask for"; a team name in either slot (or in **Checks to run**) is the same trap as leaving it blank -- name the individual, per Direct-answer-first above.
- **Proposed window:** -- a range, a multi-day span, or "any time works" in place of one explicit start timestamp and one explicit end timestamp is not what SLM's start-date/end-date checklist asks for; state both explicitly, and never fold post-deployment monitoring time into this window even when the tier requires 24-48h of it afterward. See Direct-answer-first above.
- Risk-and-readiness item 1 -- a blast-radius or worst-case narrative with no direct one-line "No, because..." / "Yes, it would..." stated first is what draws a repeat "does this hurt our business, revenue, or client relationships?" question.
- Risk-and-readiness item 1 / Systems affected -- naming a second-order chain beyond the required direct callers (who calls the callers, not just the callers themselves) is what makes an accurate, fully-compliant answer read as alarming rather than reassuring. See Answer, evidence, mitigation above.
- Risk-and-readiness items 4-5 -- counterpart awareness stated only in passing, with no explicit "Yes -- <names> are aware and available" restatement, is what draws a repeat "are product and operations counterparts aware and available in real time?" question.

**Subject line.** `Change Submission: STCM#### - {description}` if an STCM record exists (found or given); otherwise `Change Submission: {TEAM-KEY} - {description}` -- no `(STCM pending)` or similar annotation. The team card is the change record when no STCM applies. No backticks needed here -- it's a single fixed line, not a body field.

**No-STCM change record.** When no STCM applies, do not write "STCM pending" anywhere in the draft. Drop the STCM segment from the **Change:** line -- just `**Change:** KEY-### | description` -- and omit the **STCM record:** line from LINKS entirely, leaving **Team card:** (which is now the change record) and **Change set:**.

**Address-to-confirm caveat.** The template flags that the SLM distribution address is not yet confirmed. Carry this forward every time as a **To:** line at the top of the body -- e.g. **To:** `` `✍️ SLM distribution -- confirm address with SLM before first submission` `` -- rather than guessing an address.

**Cc line.** **Cc:** `` `✍️ EM/Director (Owen Winkler); add the VP (Todd) for High/Critical -- the VP approves by replying to this email, so for those tiers the VP must be a recipient` `` -- tier is usually still a human call at draft time, so phrase the VP Cc conditionally rather than asserting a tier. (Owen's EM/Director approval is already on the PR via the gate; the VP's is the one that arrives through this email.)

**Everything else** -- copy the template's field labels (bolded) and order verbatim; drop the template's square brackets everywhere and fill each field with its sourced fact. Any field that would have no fact behind it blocked the run at step 6, so a produced email has no content blanks; the only backticked spans left are the To/Cc delivery lines.

## Service-directory cache

`.claude/cmemail/service-directory.json` (gitignored -- state, not source, like `standup-context.json`). Maps a service name to its `operationsCounterpart`, `productCounterpart`, and a dated `dependencies` snapshot, plus a `team` block recording the canonical team name and its aliases. Exists because Compass isn't active on this Atlassian instance (`getCompassComponents` fails with "Unable to find active workspace"), so there's no structured service-ownership registry to query -- this file is the substitute, and it is deliberately not fully populated: several entries are `confidence: "unresolved"` on purpose rather than guessed.

**Two different refresh models, don't conflate them:**
- **Dependency edges** are cheap and structured -- re-fetch via `mcp__plugin_datadog_mcp__search_datadog_service_dependencies` whenever current blast-radius data matters more than the cached snapshot's date.
- **Product/operations contacts** are human-confirmed, not auto-refreshable. Confluence's own ownership pages are frequently stale or mutually contradictory (that's how the `staleAliases` block and the `unresolved` entries came to exist -- cross-referencing Confluence, Jira, and Datadog's service-catalog `team` tags for these same six services turned up three different names for one team and zero named PMs for three services). Don't "fix" an `unresolved` entry by re-scraping the same pages; it needs a human answer. When you get one, edit the JSON directly and set `confirmedBy`/`confirmedAt`.

Tell Claude in natural language to update it (new service, corrected contact, resolved naming question, personnel change) -- same pattern as `standup-context.json`.

## Notes

- No backing script -- a single-ticket fetch plus a couple of linked-issue lookups is well within MCP's remit; add a script only if this later needs to fan out across many tickets.
- Requires Atlassian Rovo MCP connected. `gh` is used for exactly one thing: fetching the Change-set PR's approved reviews to source the approvers list (step 5). Everything else about the PR -- body, general comments -- stays out of scope; the PR link itself is normally read from Jira, or taken as user-provided/cross-verified if supplied directly (see step 3). The Datadog MCP is used for one thing: upstream service dependencies for Systems affected (step 4); falls back to the service-directory cache if not connected.
- Never fabricate approvals, risk narrative, named contacts, or verification/monitoring plans to clear the gate. The gate is the honest alternative to inventing: when a source genuinely covers a field (the ticket's prose, the PR, or the prompt states the fact), use it as a sourced answer; when no source does, block on that field rather than paraphrasing thin prose into a compliance claim or shipping a hedge. There is no middle "quoted excerpt, let the human decide" path anymore -- that was the draft-with-blanks behavior the gate replaces. The same rule governs the service-directory cache: an `unresolved` entry stays unresolved and blocks its field, it does not get quietly filled in.
- The approver registry (`.claude/cmemail/approvers.json`) is version-controlled, not gitignored like the service-directory cache -- it's change-process policy that must behave identically for everyone on the team, and it holds no secrets (names + public GitHub logins). Update it in natural language the same way (new EM/director, a corrected login); edit the JSON directly when you do.
